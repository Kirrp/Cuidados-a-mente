# Revisão de problemas — 12/10/2026

A revisão e as correções foram feitas na raiz atual do projeto. A cópia histórica aninhada não foi alterada. A documentação oficial do [Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/), incluindo SQLite e notificações, foi consultada antes de modificar o código.

## Problemas e motivos das correções

| Problema confirmado | Correção e por que era necessária |
| --- | --- |
| Resposta HTTP em HTML, como erro de proxy ou recusa de acesso, era tratada como falta de conexão. | O cliente mantém o status HTTP e não usa cache nem confirma uma operação offline nesses casos. Isso evita ocultar uma recusa de acesso ou apresentar como salva uma alteração que falhou. |
| Respostas e sincronizações podiam continuar depois de trocar de conta ou de uma recusa de acesso. | O cliente captura o token e a versão de acesso de cada operação e descarta respostas atrasadas. A fila não envia operações da conta anterior com o token da conta atual, e uma resposta antiga não repovoa o cache depois de uma recusa 401/403. |
| Leituras, gravações e inserções na fila offline usavam um escopo que podia mudar durante os `await`. | Cada operação captura a geração e o escopo da sessão; operações antigas são invalidadas. Isso evita devolver ou gravar dados de uma pessoa na conta seguinte. Há testes com SQLite em memória para reproduzir essas trocas. |
| Uma inserção offline atrasada podia apagar o cache da conta seguinte ou repovoar cache/fila depois da limpeza. | As mutações críticas e a limpeza executam em fila, e a limpeza invalida operações anteriores. Isso preserva o cache atual e impede reinserir dados removidos. |
| Edições/inclusões offline simultâneas podiam criar pendências conflitantes ou ultrapassar o limite de 100. | Autorização, limite e conflito são conferidos dentro da fila imediatamente antes de inserir cada pendência. |
| Uma criação podia ser gravada no servidor antes de a conexão cair; a fila gerava outro identificador ao repetir. | O identificador `mutationId` é criado antes do primeiro envio e preservado na fila. O servidor consegue reconhecer a repetição e evitar registros duplicados. Reutilizá-lo com outra pessoa ou categoria agora é recusado. |
| Atualizar uma memória permitia usar `idosoId` adulterado na validação do arquivo. | O backend valida a mídia contra a pessoa efetivamente associada ao registro. Isso impede associar uma mídia privada de outra pessoa. |
| Um vínculo vencido podia passar na verificação central de acesso. | A autorização considera o prazo de validade em cada operação. Um vínculo expirado deixa de autorizar acesso, mesmo em chamadas diretas à API. |
| Uma captura de GPS em andamento podia gravar o ponto depois de desativar o compartilhamento ou revogar a autorização. | A checagem e a gravação são coordenadas com a revogação e a exclusão do ponto. Isso impede que uma localização apagada reapareça por causa de uma captura atrasada. |
| Rotina e Relatórios podiam ocultar o seletor quando a pessoa atual não tinha registros ou permissão. | O seletor continua disponível, permitindo acessar outra pessoa acompanhada. |
| O editor de permissões podia preservar dados da pessoa anterior após erro ou resposta fora de ordem. | O estado é vinculado à pessoa correta, respostas antigas são descartadas, erros retiram o editor anterior e há nova tentativa. Isso evita salvar as permissões de uma pessoa em outra. |
| Emergência dependia de carregar rotinas, remédios e consultas para obter o telefone. | Emergência e Perfil consultam somente as pessoas quando não precisam dos registros. A emergência mostra falha e nova tentativa, evitando interpretar falha de rede como ausência de contato. |
| Acompanhamento podia permanecer carregando ao trocar uma área com consulta pendente por Contatos. | A mudança invalida a leitura anterior e encerra o indicador nas áreas sem consulta. |
| O mesmo toque em uma notificação podia navegar de novo após recarregar o usuário. | A resposta da notificação é consumida ao ser atendida, evitando redirecionamentos repetidos. |
| Atualizar lembretes durante troca de conta podia perder a nova atualização; um agendamento podia terminar depois do logout. | Atualizações aguardam a anterior e usam geração de sessão; um agendamento que termina após a saída é cancelado. Os identificadores incluem a conta e os testes reproduzem os dois casos. |
| O lembrete de uma pessoa podia abrir os registros da última pessoa selecionada. | O payload e a navegação levam a pessoa do registro, para que o toque abra o cuidado correspondente. |
| O script do backend podia executar um JAR antigo após alteração do `pom.xml`, falhar em localizar um JDK válido ou não propagar um erro. | A validade considera fontes e `pom.xml`, a busca também consulta o Java do PATH e o código de saída é propagado. Isso evita executar comportamento desatualizado ou esconder falha de inicialização. |
| O tratador genérico do backend transformava erros de requisição do Spring em HTTP 500. | Parâmetro ausente, método inválido e rota inexistente preservam 400, 405 e 404, incluindo o cabeçalho `Allow`. Assim o cliente identifica a falha correta, sem receber detalhes internos do servidor. |
| A restauração de backup verificava os arquivos do pacote, mas não sua correspondência com a mídia referenciada no SQLite. | A restauração exige banco e correspondência exata das mídias antes de disponibilizar a pasta. Isso evita aceitar uma restauração que perde arquivos ou inclui mídia extra. No Linux, os arquivos restaurados recebem permissões restritas. |
| O README indicava `npm run docs:legal`, mas o comando não existia. | O script foi registrado para que o procedimento documentado funcione. |

## Verificação e limites

| Verificação | Resultado desta revisão |
| --- | --- |
| TypeScript e ESLint | Aprovados, sem erros nem avisos de lint |
| Cliente da API | 8 cenários aprovados |
| Offline com SQLite em memória | 9 cenários aprovados, incluindo limpeza, troca de conta e edições simultâneas |
| Notificações simuladas | 6 cenários aprovados, incluindo pessoa correta e migração de avisos antigos |
| Fusos, fontes e contraste | Aprovado, com 26 pares de contraste |
| Regras do backend via Java/SQLite | 92 verificações locais aprovadas com fontes atuais |
| Maven/Java 21 | Empacotamento normal aprovado em modo offline, com 15 testes JUnit e zero falhas/erros/skips; JAR em `backend/target` atualizado |
| Integração HTTP | Aprovada com classes atuais, Java 21 e SQLite temporário: autenticação, QR, permissões, isolamento, CRUD, exclusão, CORS e persistência |
| Backup | 2 testes aprovados, incluindo subcasos de mídia ausente/extra |
| Scripts de execução | Sintaxe PowerShell e 4 cenários de validade do JAR aprovados |
| Configuração/dependências Expo | Configuração aprovada; compatibilidade aprovada em modo offline, usando os dados locais do Expo |
| Exportação web | 38 rotas exportadas após as correções |

Os testes de API, fila e notificações usam transporte/SDK simulados; o teste offline usa SQLite em memória. Eles verificam a lógica e as corridas, mas não comprovam a cifra SQLCipher, entrega de notificações ou GPS em aparelho físico. Esses recursos continuam exigindo uma compilação nativa e conferência em Android/iOS.

Os testes do backend e de backup usam bancos, chaves e mídia sintéticos. O banco persistente, as mídias reais e os segredos da instalação não foram alterados nesta revisão.

O download inicial do Maven foi impedido pelo ambiente de rede. A distribuição e as dependências já disponíveis localmente foram usadas para concluir o empacotamento normal sem rede. As classes do JAR final foram comparadas com as classes usadas no teste HTTP e são idênticas. O wrapper encontra agora a distribuição no cache local do projeto.

A exportação web das 38 rotas foi concluída. Os PDFs dos manuais não foram regenerados nesta revisão; este documento registra os motivos e o alcance das correções atuais.
